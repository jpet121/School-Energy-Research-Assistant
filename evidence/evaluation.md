# External evaluator

Run the evaluator from the workbench source directory with the same Python environment. Keep inputs, labels, raw outputs and adjudications in the evaluator's private directory, separate from the application database. Only the aggregate report is imported into the browser.

1. Use `python -m retrofit.evaluate inventory --origin http://127.0.0.1:8765 --snapshot ID --out inventory.json` to capture eligible source-span and table identities from a published snapshot.
2. Record an external coverage document with `units`. Each unit has `unit_id`, `category`, `span_ids` and `evaluator_note`. Table units also have `row_id`. Run `audit inventory.json coverage.json --out audit.json`. A missing quota or unverified span withholds freeze.
3. Supply the version 1.1 `Protocol` fields declared in `retrofit/evaluate.py`, including exact case inputs, exposure/custody, split and leakage clusters, candidate snapshots/modes and the SHA-256 of the separate label file. Gold is keyed by case ID and uses `relevance_sets` and `required_units` of alternative complete span sets. Use `freeze protocol-input.json audit.json --out protocol.json`. Development and held-out splits each contain 90 cases with the accepted strata. Retire exposed held-out clusters before forming a new benchmark.
4. Run each declared candidate against development cases with `run protocol.json --origin … --candidate NAME --split development --out NAME.json`. The app receives the exact question and context along with the snapshot/mode. It does not receive labels, expected statuses or adjudications. Run `select protocol.json gold.json NAME.json … --out selection.json` to retain the selected pipeline and comparison record.
5. Run that one selected candidate for held-out repetitions 1, 2 and 3 using `--split held_out --selection selection.json --repetition N`. Retain failures and distinct run identities. For independent results, the custodian runs scoring outside the builder account with the private gold file and directory.
6. Run `report protocol.json gold.json selection.json repetition1.json repetition2.json repetition3.json --out report.json`. Pass a separate production evidence record only when it exists. Optional human adjudications bind each exact actual generated output or failure to a qualified reviewer. Passing retrieval needs three distinct execution identities and complete attempt evidence. Passing generation also needs measured budget compliance in every repetition. Never turn fixture scores or missing denominators into an application pass.

The subcommands after step 1 also use the `python -m retrofit.evaluate` prefix. Use each command's `--help` for complete arguments. Result JSON files retain raw counts, candidate/source hashes, failure observations and per-repetition decisions. Eligibility is assessed for each repetition under D2. A failed or unmeasured generation result can leave D6 workbench-only eligibility when applicable production and retrieval gates pass. The report preserves the status of generation and does not record owner acceptance.

After separate D3 authorization and operator review of the exact hosted inputs, a future evaluator may use `run --confirmed-hosted-inputs`. This separate manifest contains only the frozen protocol hash, split, operator confirmation reference, and ordered case IDs with exact question/context pairs. The runner checks equality and applies the app's normal provider, session, eligibility, budget and timing gates per attempt. For generated-answer reporting, human `reviews` bind each outcome's canonical SHA-256, evaluator reference and adjudicated counts. Actual outputs stay in the evaluator's raw run records.

A failing imported generation report places a persistent safety hold. Rerun the affected frozen evaluation with the same candidate and generation model, then import the later report with distinct run and output identities and corrected adjudication. The importer checks all repetitions and the original failed cases before clearing the report hold. A historical report with missing regression evidence still requires new verified evidence.

A provider-budget hold persists across restarts. Use **Local controls** to record each dispatched attempt's confirmed actual charge and billing reference. The same operation is available at `POST /generation/{operation_id}/attempts/{attempt}/reconcile`. The ledger retains unresolved reservations and any amount actually charged above the reservation.

For a later corrective evaluation, preserve the original frozen execution file. After recording billing on the workbench that performed the authorized experiment, run `python -m retrofit.evaluate billing --origin ORIGIN --execution repetition.json --out billed-repetition.json`. This verifies the recorded operation identity and writes a new file bound to the original execution. Completed observations retain all fields outside billing. Evaluator timeouts and transport failures retain their original error classification and can recover later attempt evidence from the same recorded operation and retrieval. Bind adjudications to the refreshed evidence.

For an affected input outside the held-out questions, capture its separately recorded corrective operations with `python -m retrofit.evaluate billing --origin ORIGIN --operations OPERATION_ID --out budget-case.json`. Give the three repetition-specific files to `report --budget-regressions FILE1 FILE2 FILE3`. The distinct targeted operations can finish before or after their corresponding held-out runs. The report records the interval covering both sets of evidence, and recovery checks that the entire interval follows the hold. Use the same effective question, context, retrieval mode, edition filters, frozen snapshot, eligibility and packed evidence, and the same provider model, tokenizer, rates and budget policy. Each targeted case must return a validated result, and every dispatched attempt must have a valid reservation, in-time dispatch, bounded usage and confirmed billing. Supplemental budget regressions do not contribute to held-out semantic scores. Any live corrective run still requires separate D3 authority, exact-input confirmation, and accounting against the authorized attempt and cost limits. The held workbench does not dispatch a corrective request or reset spend history.

Import the later report with the applicable D6 production, retrieval and generation gates recorded as passing. Enter its SHA-256 under **Local controls** to resolve the hold. Resolution checks the remaining budget and leaves generation disabled until the operator uses the normal enable control. Receipt consistency depends on authorized evaluator custody and the retained raw evidence. When a separately authorized live evaluation uses a different store, the experiment owner must allocate its cost and attempt limits before any dispatch and apply the remaining allocation to the original store's D3 policy before resuming. Each store enforces its own allocation. A separate store does not create a new M1 allowance.
